# 实时画面异常断线恢复

## 目标与范围

修复 VPN / NAT 穿透短暂断网后，播放页停留在 WebSocket 1006、不能恢复的问题。
只改独立播放页及其回归测试，不改摄像头采集、后端编码、记录筛选或设备控制。

## 证据与原因

- 现场四路 WS 同时报发送堵塞，一路随后 send liveness timeout；摄像头仍持续解码。
- 现有 close handler 只显示错误；原看门狗只检查 OPEN，CLOSED 永远不会再触发连接。
- 主机 CPU 压力和 VPN 链路都可能是首次堵塞的诱因；本修复不声称消除这些原因。

## 方案

- 临时关闭码触发单个重试定时器，1 / 2 / 4 / 8 / 16 / 30 秒指数退避并加抖动，最高 30 秒。
- 收到实际播放画面才重置退避，不因一次握手成功就清零。
- 正常关闭、策略拒绝、后端明确的摄像头错误不自动重试，保留错误原因。
- 手动重连/切相机/切通道取消旧定时器；旧 socket 迟到事件不影响新连接。
- 握手或 OPEN 无首条消息长期挂起也可进入退避重试；页面离开取消重试，bfcache 恢复可重新连接。
- 利用 Node VM 执行真实 watch.html 内联脚本，模拟 socket 与时间；不增加测试依赖。

## 阶段与验证

- 规划完成；在最新 upstream/main 的独立 worktree 开发，原工作区和部署保持不动。
- 先补回归测试，确认旧代码失败，再实现最小修复。
- 旧实现：21 项回归测试中 15 failed、6 passed；修复后 21 项全部通过。
- 完整验证：34 个测试文件通过，621 passed、1 skipped；TypeScript 与 Vite production build 通过。现有超过 500 kB 的 bundle warning 保留，不扩大为拆包改造。
- 当前阶段：实现与验证完成，进行最终差异审计和独立 PR 提交。仅提交本修复一次；不自动追逐下一轮 review 或部署。
- 自动化覆盖真实内联脚本，但尚未进行真实 VPN 断网/恢复的浏览器验收；现场 CPU 和网络拥堵的最初诱因未在本 PR 修改。
