# 设备状态容器

## 背景与目标

Agent 与规则引擎要能回答「客厅的灯现在是开还是关」「人在传感器现在检测到有人吗」。这类问题需要一个单独的落点存**当前值**，而当前值来自多个异构来源：启动时从云端拉一遍、设备状态变化时推送过来、设备上线时补拉缺的那部分。

设备状态容器就是这份「当前值」的唯一落点：多个来源往里写，消费方按路径模式订阅变化、按路径模式取一致快照。

**它只装状态，不装事件。** 能问出「现在是什么」是职责边界；「发生了什么」（带时序、可回溯）走 `dispatch/dispatcher.py`，两者不混。

---

## 产品面

### 能做什么

- **按路径问答**：任意叶子可读（某台设备在线吗、某条属性现在是多少），树的任意子树可整体快照
- **变化订阅**：按路径模式订阅，只在值**真的变了**时收到事件，事件自带变化前后的值
- **有效期**：写入时可设置有效时长；默认永久有效。到期默认删除并发送 `Change(reason="expire")`，也可保留元数据供查询方识别过期
- **可观测**：树有多大、队列多深、各道闸拦下过多少次，以及整棵树的文本转储都有对应端点（见「相关 API 路径」）

### 能力边界

- 只装**米家设备**的状态。感知、身份、家庭记忆各有自己的存储，不在这里
- 只有当前启用家庭的设备在树里；切家庭 / 切号会清掉整棵树再重建
- **设备离线时只更新在线标志、不更新属性**。云端返回的是它缓存里的最后一次上报，可能是任意旧值；写进去会把「最后上报时刻」刷成当下，而响应不带时间戳，消费方分辨不出它已经过期。整台不写也不行 —— 容器里没有这台设备，消费方就分不出「离线」和「没接入」

## 研发面

### 架构概览（数据流图）

```
       ┌─ 启动对齐（state_align）─── 整代跑一次，主动拉一遍
云端 ──┼─ 状态推送（state_push）──── 只在值变化时来（走哪条通道见「与其他模块的关系」）
       └─ 上线补拉（state_push）──── 只补容器里缺的叶子
                    │
                    ▼
        StateStore（state/store.py）
        路径词表 iot/device/<did>/status/online
                 iot/device/<did>/prop/<siid>.<piid>
                    │
        ┌───────────┼──────────────┐
        ▼           ▼              ▼
  规则引擎 iot 源  调试/排障端点   在线标志消费方
 （按 pattern 订阅）（stats / dump）
```

**每笔写入都带来源标记**，排障时先看标记就知道该翻哪本日志：

| 标记            | 谁写的                                                         | 排障方向        |
| --------------- | -------------------------------------------------------------- | --------------- |
| `iot_align`     | 启动对齐；**上线补拉也用它**（对补拉来说它就是一次迟到的对齐） | 那次对齐 / 补拉 |
| `iot_push`      | 状态推送。云端与本地中枢**共用**这个标记 —— 容器不区分通道     | MQTT 推送日志   |
| `iot_refresh`   | 云端重拉在线标志                                               | 那次刷新        |
| `iot_reconcile` | 设备移出当前家庭后的清理                                       | 作用域变更      |

### 核心模块

| 类 / 模块                      | 文件                  | 职责                                                                                 |
| ------------------------------ | --------------------- | ------------------------------------------------------------------------------------ |
| `StateStore`                   | `state/store.py`      | 树本体：写入、判等产事件、按 pattern 订阅与快照                                      |
| `Entry` / `Change` / `MISSING` | `state/types.py`      | 叶子、变更事件、不存在哨兵                                                           |
| `IotPushWriter`                | `miot/state_push.py`  | 推送与补拉两条通道写容器的统一入口，作用域与在线闸门都在这一处判                     |
| 启动对齐                       | `miot/state_align.py` | 整代跑一次，按当前家庭拉设备属性写进容器；同时给补拉提供「容器里缺哪些叶子」的读取端 |
| iot 源                         | `rule/iot_source.py`  | 主要消费方：按 pattern 订阅属性与在线标志，把当前值判成规则条件项的布尔              |

### 关键设计决策

#### 值只能写叶子，不能写父路径

容器的 `set` 是**替换**语义：写某个子树路径，该子树下未被新值覆盖的叶子会被删掉。所以「整台设备写一次」和「逐叶子写」是两条方向相反的路 —— 对齐那侧两条都有（整台写一次，被容器拒收时退化成逐叶子），而推送侧只能逐叶子。

#### 值真变才产事件

同一个值重复写入不产事件，判等带**精确类型**（`True` 与 `1` 判为不同 —— 设备把布尔属性时而报数字时而报布尔很常见）。

这不只是省事件：**属性推送按设备只挂一条源，换源时的重叠窗口会重复投递同一条变更，靠的就是这里判等吃掉**，见 [设备控制](device-control.md#属性推送同样选路但按每台设备只有一个源)。

同一个值被两个来源先后写入时，`last_changed` 不动，但 `last_reported` 与 `source` 都会更新成后写的那个 —— 「值没变」和「没人再报过」是两件事。

#### 有效期与过期通知

`StateStore.set` 的 `expires_in_ms` 缺省表示永久有效。设置有效期后，默认到期删除叶子，并向匹配的订阅方发送一条 `Change`：`new=MISSING`、`reason="expire"`、`source="state_expire"`。因此规则等状态消费者会自然回到「路径不存在 / 未就绪」。

如果写入指定 `on_expire="retain"`，叶子不会从内部树删除，但 `get` 和不带元数据的快照不会再返回它；带元数据的 `get_entry` / `snapshot(with_meta=True)` 会看到 `expired=True` 与 `expires_at`，并收到一条 `old == new`、`reason="expire"` 的通知。

刷新同一路径会替换旧的有效期。过期调度器会校验路径当前的 `expires_at`，旧定时器不能删除或标记新值。

`None` / `0` / `False` / `""` 都是合法状态值，所以「不存在」用单独的 `MISSING` 哨兵，且**它进布尔上下文会抛异常**：iot 规则正是拿「路径不存在」表达未就绪态的，`get(path) or fallback` 这类写法会把这个语义混掉。

#### 作用域两道闸，对应两种失效

- **换作用域**（切号 / 切家庭）用「已对齐的代号 == 当前代号」判 —— 代号一推进就自动失效。挡的是：授权新账号时旧 MQTT 连接还没拆，那段窗口里旧账号的推送会写进刚清空的树
- **掉出作用域**（同一代之内某台设备搬出当前家庭）用设备集判 —— 代号是全局的，挡不住单台的搬出；那种情况删除调和已经删掉了它的叶子，一条在途推送会把它整个写回来，变成谁也删不掉的幽灵设备

上下线那条**只过第二道闸**（切号时启用集会先被清空，而「按家庭过滤」对空启用集一律返回假，那个窗口是失败关闭的）；**属性推送多一道对齐门** —— 对齐拿的是云端缓存的最后一次上报、推送拿的是实时值，两者都不带时间戳，谁覆盖谁只能靠顺序定死（先对齐再落推送）。

#### 叶子与子树不能混在同一层

一个路径是叶子还是子树由数据本身决定，写入方并不声明。形态在两种之间翻转时，订阅旧形态的消费方会在收到一个删除事件之后**再也收不到**，所以容器显式计数并告警，不指望靠数据躲开。

#### 有闸，且失败是「拒绝而不抛」

叶子总数与写入级联深度各有上限（级联用于「回调里再写容器」，成环时靠它断开）。撞上限时**整笔被拒却不抛异常**，调用方只能靠返回值知道 —— 所以不看返回值的地方，写入可能是静默丢失的。

订阅另有一个「订阅号」机制，挡掉「这批事件提交之后才订阅」的人：订阅方不会收到自己订阅之前的历史事件。

### 如果我要修改设备状态相关功能

| 修改目标                               | 去看哪个文件                                                              |
| -------------------------------------- | ------------------------------------------------------------------------- |
| 改路径词表 / 判等语义 / 上限           | `state/store.py`、`state/types.py`                                        |
| 改推送或补拉的写入闸门                 | `miot/state_push.py`                                                      |
| 改启动对齐范围（拉哪些设备、哪些属性） | `miot/state_align.py`                                                     |
| 改规则怎么读容器                       | `rule/iot_source.py`                                                      |
| 改容器清理（切家庭 / 设备搬出）        | `miot/client.py` 的 `_sync_iot_online_flags` / `_reconcile_iot_deletions` |

### 相关 API 路径

`GET /api/miot/state/stats`（树规模、队列深度、各道闸拦下的次数）与 `GET /api/miot/state/dump`（按 pattern 的文本转储，每叶子一行、按路径排序，两次 dump 可直接 diff）。端点在 `miot/router.py`。

### 与其他模块的关系

**上游**：属性值有两个来源 —— 启动对齐与上线补拉走**云端按需拉**；实时变化走**状态推送**。推送走哪条通道由 [设备控制](device-control.md#属性推送同样选路但按每台设备只有一个源) 决定（云端 MQTT 或本地中枢，按设备选一条源），容器这一层不区分，两种都落 `iot_push`。

**下游**：规则引擎的 iot 源按 `iot/device/*/prop/*` 与 `iot/device/*/status/online` 两个 pattern 订阅，把当前值判成条件项的布尔；判不出来时置「未就绪」而**不是喂假** —— 假会驱动一次凭空的退出边沿。见 [规则自动化](rule-automation.md)。

**互动**：scope 变更（切家庭 / 切号）由 `MiotService` 统一走「重建容器 → 建启用集 → 重新对齐」的顺序；设备移出当前家庭由 `MiotProxy` 的刷新路径做删除调和。
